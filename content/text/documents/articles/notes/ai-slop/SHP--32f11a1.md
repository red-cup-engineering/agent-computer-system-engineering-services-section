# Semantic Hypertext Packet Profile

Status: draft.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL in this document are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in all capitals.

## 1. Role

A Semantic Hypertext Packet is a finite hypertext projection from an EAVT trace frontier.
It is not the trace itself.
It is the settled, inspectable packet form used when SPOTCOMP needs human-readable hypertext that still carries enough structure for machine inspection.

SHP is a SPOTCOMP sibling of TRC, not a child of TRC.
TRC is the typed resource catalog and memory surface; SHP is the semantic hypertext packet surface.
A TRC resource may produce or store an SHP packet, but that storage relationship does not make SHP a TRC-local format.

The current source-backed identity rule is:

- `class` names the morphism identity that produced the element;
- `data-*` attributes carry input-carrier coordinates for that morphism;
- element contents carry the output carrier, which may contain nested carrier elements;
- the whole HTML document is the top-level carrier.

## 2. Packet Object

An SHP object MUST declare:

- a source trace or trace family;
- a finite trace frontier;
- finite settlement evidence;
- the projection morphism;
- the output carrier `html-document`;
- evidence for the projection.

An SHP producer MUST be deterministic for a fixed trace frontier and projection rule set.
SHP projection is monotone: adding trace evidence may add packet structure or produce a later settled packet, but it does not authorize mutating the historical packet evidence in place.

## 3. Document Requirements

An SHP document MUST be an HTML document with:

- UTF-8 character encoding;
- no executable scripts;
- no required external resources;
- semantic elements whose `class` values name the morphism, generator, or projection role that produced the element;
- `data-*` attributes carrying the relevant EAVT source coordinates or frontier references when available.

For RFC-shaped SHP packets, RFC 7992 is the current inhabitant profile.
RFC 7992 is not the definition of SHP itself; it is a concrete HTML profile whose structural classes already satisfy the SHP class-as-morphism-identity rule for RFC publication objects.

The RFC 7992 inhabitant profile requires:

- `<!
  DOCTYPE html>`;
- `<html lang="en">` with root class derived from series information;
- `<meta charset="utf-8">`;
- LF line endings;
- double-quoted attribute values;
- no required external image, CSS, or script dependencies for packet semantics;
- structural classes such as `bcp14`, `xref`, `eref`, `relref`, `selfRef`, `artwork`, and `sourcecode`.

SHP tightens packet safety by requiring no executable scripts for inspection.

## 4. Trace Linkage

An SHP projection SHOULD identify:

- the source trace or trace family;
- the frontier identity used for projection;
- the projection rule set;
- the modeled player or local process that produced the projection.

This linkage MAY appear as EAVT rows, HTML metadata, embedded JSON, or all three.
If embedded JSON is signed or hashed, it MUST use the canonicalization rules in [IETF-CONFORMANCE.md](./IETF-CONFORMANCE.md).

## 5. Class Names

Class names are structural names, not styling hints.
A class SHOULD name the morphism or projection role responsible for the element.

When a standard HTML element already carries adequate semantics, the element name and the SPOTCOMP class name should agree rather than compete.
For example, a title projection can use:

```html
<h1 class="has-title" data-e="doc:hello">Hello SPOTCOMP</h1>
```

For RFC 7992 classes, the class vocabulary is already structural.
For example, `bcp14` names the morphism that marks a requirement keyword, and `xref` names the morphism that renders a local cross-reference.

## 6. Packet Safety

An SHP document MUST NOT execute code during inspection.
Implementations SHOULD treat inbound SHP as untrusted input and parse it with an HTML parser configured for no script execution.

## 7. Declaration Probe

[schema/shp-profile.schema.json](./schema/shp-profile.schema.json), [examples/shp-profile.json](./examples/shp-profile.json), and [src/shp-profile.mjs](./src/shp-profile.mjs) define a candidate checker.

The probe checks:

- SHP is declared as a finite `html-document` packet object;
- trace frontier, settlement evidence, and projection morphism are present;
- projection and markup directions are deterministic and monotone;
- class names are declared as morphism identities;
- `data-*` attributes are declared as carrier coordinates;
- no alternate plain-text packet profile is declared;
- RFC 7992 is represented as an inhabitant profile with its byte-level constraints;
- packet safety forbids script execution and required external resources.

The probe does not prove the SHP object derivation, HTML parser correctness, full RFC 7992 conformance, or the placement of the SHP projection morphism relative to settling and TRC.
