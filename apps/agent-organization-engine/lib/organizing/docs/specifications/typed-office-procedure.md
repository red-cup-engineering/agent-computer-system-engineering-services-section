# Typed office procedure leaf

Status: proposed source refinement, 2026-10-14. Native installation and independent operational receiving remain separate from source tests.

## Purpose and existing model

A qualified office performs an already-defined pure method without asking inference to reinterpret that method on each occurrence. The real first procedure plans the complete module/schema/assay output of an admitted artifact fabrication specification. The planner supplies a dependency/build work item; it does not fabricate, install, publish, deploy or accept its own output.

Specification-driven development here uses model-based systems engineering and stepwise refinement. [INCOSE's MBSE initiative](https://www.incose.org/group/mbse-initiative/) places modeling across requirements, design, analysis and verification; [NASA's system design process](https://www.nasa.gov/reference/4-0-system-design-processes/) connects stakeholder expectations, technical requirements, logical decomposition and design solution. The following concrete refinement uses the existing Group Work/Action/office/skill and typed operation models. Naming stages or passing text between prompts is not evidence of semantic refinement.

World requirement: the responsible office can repeatedly obtain the same complete fabrication plan for one exact settled order and installed implementation, and only received predecessor work enables a dependent consumer.

Machine guarantee: resolve one current ready allocation, admit its immutable typed procedure binding, invoke the selected addressed pure operation through the existing authorized RPC path, and propose its actual typed outcome with witnesses. Existing independent receiving determines settlement. Environment assumptions: the selected genuine provider composition is qualified, the declared pure implementation obeys its effect contract, and the execution runtime meets its provider requirements. This change is not a sandbox proof.

## Requirements and test oracles

- R1. A typed procedure shall invoke the exact operation declaration, executable body and schema graph named by its binding. Changing bytes while retaining a schema ID changes its signature. Oracle: altered ref/signature/schema/body is refused before invocation.
- R2. A typed procedure shall execute one admitted concrete input without inference interpretation. Oracle: actual captured planner returns its exact ordered paths and specification digest while an inference spy remains at zero calls.
- R3. A typed procedure shall use current office delegation, held capability and pure/safe/coordination-free deterministic operation standing. Oracle: unheld, unallowed, effectful or ambient host callback variants do not execute.
- R4. A typed procedure shall admit input against its closed domain graph and output against its closed codomain graph, then evaluate its separate work-specific acceptance schema. Oracle: wrong input/output type fails; well-typed wrong result has false acceptance. Prior mutable schema registrations cannot change this result.
- R5. A typed procedure shall preserve proposal and independent receiving as distinct transitions. Oracle: successful invocation alone leaves the duty unsettled; exact independent receipt/discharge unlocks its existing dependent.
- R6. An admitted binding shall preserve a complete immutable JSON snapshot. Oracle: mutation of the caller's input or acceptance object after admission cannot alter executed meaning.
- R7. Existing command bindings shall preserve their current admission, execution and exact result gates. Oracle: existing allocated-deterministic-effect regression still succeeds and revocation still prevents execution.
- R8. Repeated execution/recovery shall retain existing allocation, reservation, invocation and proposal identities. Oracle: interrupted work is reconciled through existing completion ports; pure replay cannot produce an unreceived discharge. No exactly-once external-effect guarantee is introduced.

## Allocation and architecture

`office bears duty → duty names work and permitted skill → structured intent binds work/skill and dependencies → canonical office-service allocation → signed Action and ready frontier → declared provider → governed RPC invocation → native result proposal → independent receiving/discharge`.

The source of structural readiness remains Organizing's work readout/dispatch. The clock schedules existing operations; it does not invent work policy. Enterprise attention and allocation succession remain upstream selection concerns. A changed instruction must change eligible/current work through those owners, not through an executor's prose interpretation.

The existing deterministicExecution carrier gains a disjoint typed-operation variant:

- operation: exact native operation ref; no verb fallback
- signature: SCA identity of the existing operationDescriptor, including complete closed domain/codomain graphs and effects
- procedure: SCA identity of the canonical skill, closure kind, method and required capabilities
- request: concrete admitted JSON input
- acceptance: self-contained anonymous result schema evaluated in a closed schema universe

Only addressed JavaScript programmes or SEN terms qualify. A host callback declaration includes a verb but does not identify implementation bytes; it does not qualify. `javascriptProgram` captures the actual installed source import graph, including static JSON imports, and ordinary operation execution uses those captured bytes. The source-owned planner adapter unwraps input.workOrder; it grants no capabilities.

Code owns artifact specification admission, meaning-closure admission, realization-plan admission and path projection. The pure planner shares those implementations with derivation. It consumes existing requirement/constraint/acceptance/traceability carriers and returns their specification digest. Planner paths are one refinement observation, not proof that each requirement's semantics has been satisfied. Derived source behavior and independent consumer acceptance remain later obligations.

## Runtime and recovery

1. Existing work service reserves a currently ready allocation and records started execution.
2. Existing provider verifies delegated operation/effect membership; worker verifies held current capability.
3. Shared admission checks immutable procedure identity, exact operation/schema signature, addressed body, pure effects and closed input type.
4. Ordinary RPC dispatch rechecks authorization and records causal witnesses. No direct operation callback bypasses dispatch.
5. Closed output typing and acceptance determine a native success/error proposal. The original raw result remains available as returned for the work's declared codomain.
6. Existing proposal/receiver/discharge machinery performs independent acceptance. The executor never emits discharge.

Recovery stays in existing readCompletedAgencyWork/recoverAgencyWork ports and witnessed proposal state. Source publication, deployed operation catalogs, actual office allocation and receiver acceptance are separate evidence. New source alone establishes none of them.

## Coherent implementation ownership

- Computer Engineering AOE/lib/organizing/src/work/schema.mjs: authored carrier, identity/admission and acceptance; test/work/typed-procedure.test.mjs.
- FeltOS src/agents/worker.mjs: current governed leaf consumer; existing work/agency-work-provider.mjs and work/service.mjs retain delegation/proposal/recovery ownership.
- Code Development Engine src/fabrication/operations.mjs and plan-jsnode-modules.mjs: existing planner native declaration becomes addressed executable body; extend existing planner proposal PR34.
- Code Engineering jsnode-package-services-section: pure planner/path projection and static schema source; derive/projector preserve their existing public exports through imports/reexports.

Integration orders supplier source and public export first, addressed native planner second, shared carrier and consumer coherently afterward. Existing command consumers remain valid. Old readers do not accept the new binding; activate typed allocations only after both sides are selected and actual provider tests pass. No new scheduler, procedure registry, deployment or mutable callback registry is added.

## Verification boundary

Run actual provider tests over the complete qualified source/import/export composition. The direct Organizing test proves carrier/operation behavior, not the full service. The planner-module-closure test checks captured schema bytes; planner-behavior tests execute the actual captured pure planner. The FeltOS allocation test must retain capability, no-inference and independent receiving assertions. A missing provider export is a composition blocker, not a candidate regression and not permission to add a test shim.

The requested organizational scale remains a load-validation requirement. This bounded leaf avoids one inference round trip per deterministic occurrence; it does not establish throughput for hundreds of offices, thousands of duties or tens of thousands of skills. Measure the existing scheduler/readout/indexes under that representative workload separately, preserving its finite worker and per-tick bounds.

Carrier-family receiving also covers obligations.mjs serialization and observations.mjs decoding; both preserve the full typed binding. The legacy duty-discharge command executor refuses typed bindings before invoking its runner, directing them through allocated provider execution.
